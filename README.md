# tns-desktop-download

The public **download + auto-update site** for TchatNSign Desktop, served via
GitHub Pages at <https://tchat-n-sign.github.io/tns-desktop-download/>.
Everything here is **generated by the release pipeline** — don't hand-edit
`index.html` or `latest.json`.

The repo is public because GitHub Pages on a private repo needs Enterprise. Only
built binaries are public; the source (`Tchat-N-Sign/tns-desktop` + the
`luge-desktop` shell it brands) stays private. Same posture as the sibling
`luge-desktop-download`.

## What's served

| File / dir | What |
|---|---|
| `index.html` | The download page. Generated by `build_download_page.py`. |
| `latest.json` | The Tauri updater manifest (version + per-platform minisign-signed URLs). The app polls it — its endpoint is baked into the binary via `tns-desktop/tauri.json`. |
| `releases/desktop/` | Installers (`.dmg` / `.exe` / `.msi` / `.deb` / `.rpm`) + updater artifacts (`.app.tar.gz`, `.sig`). |
| `tns-logo.png` | The page logo — copied from `tns-desktop/icons/128x128@2x.png` on each deploy. |
| `build_download_page.py` | The page generator. |
| `.nojekyll` | Tells GitHub Pages not to run Jekyll over the site. |

## How it's updated

On a `v*.*.*` tag in `Tchat-N-Sign/tns-desktop`, its
`.github/workflows/release.yml`:

1. builds + signs the 3-OS artifacts and attaches them to a (private) GitHub
   release on `tns-desktop`;
2. **`deploy-website` job** — clones this repo, wipes and refills
   `releases/desktop/`, moves `latest.json` to the root, rewrites its
   `github.com/…/download/` URLs to Pages URLs (the source release is private, so
   the URLs tauri-action writes would 404), regenerates `index.html`, then
   **force-pushes a single orphan commit**.

> ### History is intentionally a single commit
> This is a *generated mirror*. Keeping every past release's installers (~200 MB
> a release) in git history would bloat the repo into the gigabytes, so each
> deploy resets `main` to a fresh orphan commit. **Don't expect git history**, and
> a deploy must always **clone first** — anything committed here between two
> releases is gone at the next deploy unless the workflow puts it back.

That last point is the one that bites: `build_download_page.py` and this README
live *here*, not in `tns-desktop`, so the deploy's `git add -A` carries them
forward. Edit them on `main` here; don't expect an edit to survive if you also
delete it from the clone.

## Channels and release assets (TNSD-118)

> **Status.** The generator below already does all of this. The deploy job in
> `tns-desktop` still copies installers into `releases/desktop/` as described
> above; it adopts the layout below in TNSD-268. Until then every step of
> "How it's updated" is exactly as written.

Two apps ship from here, **prod** ("Tchat N Sign") and **dev** ("Tchat N Sign
Dev", for the team), and they install side by side.

**Why the installers leave git.** `releases/desktop/` weighs 267 MB (the `.deb`
and `.rpm` are 83 MB each, GitHub refuses a file over 100 MB), every deploy
re-uploads all of it, and a second channel in the same tree would double that
against Pages' 1 GB site limit. Installers become **assets of a GitHub Release on
this repo**, one release per version and channel, and the site keeps only small
files.

| Where | What |
|---|---|
| Release `vX.Y.Z` (marked latest) | prod installers and updater artifacts |
| Release `dev-vX.Y.Z` (pre-release) | dev installers and updater artifacts |
| `/index.html`, `/latest.json` | prod page and updater feed. **Never move them**: installed apps poll this exact URL |
| `/dev/index.html`, `/dev/latest.json` | dev page (`noindex`, no screenshots) and feed |

Target deploy order, per channel: upload the release assets **first**, then
write the feed and the page. A feed that names assets which are not up yet sends
every running app that sees the new version to a 404 when it downloads. An app
never needs to be told where a binary lives, only the feed: it follows whatever
URL `latest.json` names.

## Regenerate the page locally

```sh
# prod page, buttons pointing at the files in releases/desktop/ (how it linked before channels)
python3 build_download_page.py 0.5.1 releases index.html

# a channel page, buttons pointing at that release's assets
python3 build_download_page.py 0.5.1 releases index.html     --channel prod --tag v0.5.1
python3 build_download_page.py 0.6.0 releases dev/index.html --channel dev  --tag dev-v0.6.0
```

`<releases_dir>/desktop/` holds the installers; they are listed for their names
and sizes. With `--tag` the buttons link to
`https://github.com/Tchat-N-Sign/tns-desktop-download/releases/download/<tag>/<file>`.
Without options the output is byte-for-byte what this script produced before
channels existed (`fixtures/index.prod-0.5.1.html` is that page, generated by the
original script, and a test compares against it).

**`--channel dev` requires `--tag`.** Without one the buttons would link to
`releases/desktop/` in the tree, which from `/dev/index.html` is a folder that does
not exist, and at the root is prod's installers under a banner that says "dev". Only
prod keeps the historical mode with no tag. An empty `--tag ""` is refused for either
channel (it is a variable that did not expand, not "no tag").

It exits non-zero, before writing anything, so a page already published is left
alone, when `releases/desktop/` holds no installers — a page with no download
buttons would silently replace a working one — when a dev page has no tag, and when
`--tag` does not name the channel and version it is paired with (`vX.Y.Z` for prod,
`dev-vX.Y.Z` for dev), so a dev page can never link prod's installers.

## Tests

```sh
python3 -m unittest -v
```

Standard library only. This repo has no CI, so run them before pushing a change to
`build_download_page.py`.

## Note on installer signing

Installers are signed at the OS level (Apple Developer ID + notarization, Windows
Authenticode via the GlobalSign EV cert) and verified by the release workflow, so first
launch shows no Gatekeeper / SmartScreen prompt. Auto-update integrity is separate:
every artifact in `latest.json` carries a minisign signature verified against the
public key compiled into the app.
